# ADR 0002: M2 Patient Identity Ownership and Creation

## Status

Accepted for M2 implementation on 2026-08-08.

## Context

Authentication and lifelong patient identity must remain separate. New PATIENT
registrations need complete patient identity data, while accepted M1 databases
may already contain PATIENT users without profiles. Minor profiles will later
exist without login accounts. Placeholder identities are forbidden.

## Options considered

1. Create empty profiles for M1 users through a data migration. Simple linkage,
   but invents invalid identity data and Digital IDs for incomplete records.
2. Keep all profile creation separate from registration. Backward compatible,
   but permits every new PATIENT account to remain detached from identity.
3. Create profiles transactionally for new registrations and expose one legacy
   completion operation for existing PATIENT users.

## Decision

Choose option 3.

- New registration requires a nested `patient` object and atomically creates
  User plus PatientProfile.
- Existing M1 PATIENT users receive no fabricated migration data. They may call
  `POST /api/v1/patients/me/` once with complete identity fields.
- `PatientProfile.user` is a nullable one-to-one relation. Null supports future
  minor profiles; M2 APIs never create null-owned profiles.
- `GET` and `PATCH /api/v1/patients/me/` operate only through authenticated
  ownership. No UUID or Digital-ID lookup API exists.

## Digital ID decision

Use `PT-XXXX-XXXX-XXXX`. Twelve characters use a 32-character, ambiguity-safe
alphabet generated by `secrets.choice`, giving 60 random bits. Database
uniqueness is authoritative. Service retries collisions with transaction
savepoints and fails closed after ten collisions. ID contains no PII and grants
no authorization.

## Identity-field decisions

- Sex API values: `FEMALE`, `MALE`, `UNSPECIFIED`.
- Blood groups: `A+`, `A-`, `B+`, `B-`, `AB+`, `AB-`, `O+`, `O-`, `UNKNOWN`.
- Nationality stores uppercase ISO 3166-1 alpha-2 syntax. M2 validates exact
  two-letter syntax without adding a country/location subsystem.
- Identity status starts `UNVERIFIED`; foundation values are `UNVERIFIED`,
  `PENDING_VERIFICATION`, `VERIFIED`, and `REJECTED`.
- Patients cannot write ownership, UUID, Digital ID, identity status, or audit
  fields. Verified full name, DOB, sex, and nationality are locked for later M3
  controlled-change workflows. Blood group remains self-service.
- Age is computed from `timezone.localdate()` and never stored. Feb-29 births
  advance age on March 1 in non-leap years.

## Trade-offs

- Registration gains required patient identity input, intentionally changing
  its M1 request schema.
- Legacy completion adds one temporary-compatible POST operation.
- Syntax-only nationality validation accepts reserved/unassigned two-letter
  values; full country reference data remains deferred.

## Consequences

Patient identity remains complete, ownership remains explicit, and future minor
support requires no relation migration. M3 may add identity documents and
verified-change workflows without changing M2 public identifiers.
